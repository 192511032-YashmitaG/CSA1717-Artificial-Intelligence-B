TASK 1 – DESIGN THE AGENT AND SEARCH ALGORITHMS

Scenario
A hospital robot carries medicines from the pharmacy to wards. Locations are graph vertices and corridors or lifts are edges. Each edge has a travel-time cost.

PEAS
Performance: reach the requested ward safely, correctly and with low travel time; avoid blocked corridors; use limited battery efficiently.
Environment: hospital corridors, junctions, lifts, pharmacy, wards, patients, staff and temporary obstacles.
Actuators: wheels, steering, lift interface, display and audio alerts.
Sensors: camera, LiDAR or proximity sensor, wheel encoder, lift status and location sensor.

Environment classification
Partially observable in practice because sensors can miss people or obstacles; sequential because each move affects later choices; dynamic because people and corridor conditions change; mostly discrete for graph locations and actions; single-agent for route planning although people affect the environment; stochastic in practice because travel and sensing can be uncertain. The simplified experiment is deterministic and fully observable so the search algorithms can be compared consistently.

View of AI
The robot follows the acting-rationally view. It selects actions that best achieve its goal using the available model and information. It is a problem-solving agent because it formulates a goal and searches for an action sequence. This follows the early symbolic problem-solving tradition in AI, where a problem is represented by states, operators and a goal test.

Problem formulation
State: current hospital location. Initial state: pharmacy node. Actions: move along an outgoing corridor/lift edge. Transition model: the selected edge leads to its connected location. Goal test: current node equals the requested ward. Path cost: sum of edge travel times.

Three different uninformed strategies
1. Breadth-First Search (iterative queue): expand the shallowest unexpanded location first. It is useful when each move has equal cost and a shortest number-of-moves route is required.
2. Depth-First Search (iterative stack): follow one branch as far as possible, then backtrack. It uses less frontier memory on many deep, narrow searches, but does not guarantee the shortest route.
3. Iterative Deepening Depth-First Search (recursive depth-limited search): run recursive depth-limited search with limits 0, 1, 2, ... until the goal is found. It combines low memory use with shallowest-depth solution discovery when step costs are equal.

Pseudocode
BFS: enqueue(start); mark start; while queue not empty: remove front; if goal return path; add each unseen neighbour and record its parent.
DFS: push(start); while stack not empty: pop top; if goal return path; push unseen neighbours in reverse order and record parents.
IDDFS: for limit = 0 upward: call recursive_DLS(start, limit); return when a path is found. DLS returns at the goal, stops at limit zero, otherwise recursively visits unvisited path neighbours.

Preprocessing
Build an adjacency list once and keep a visited/parent structure to avoid repeated expansion. Graph construction and parent/visited storage must be counted when reporting total memory and total runtime. For weighted corridors, use uniform-cost search rather than assuming BFS returns the least-time route.
